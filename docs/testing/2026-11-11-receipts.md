# Receipt fixes and app audit - 11 November 2026

Receipt PDF sharing and the reproduced scanning defects are fixed in this source update. The full application device suite is **not passing**. Existing release APKs were not replaced.

## Changes

- Saved expenses can share a formatted PDF with their total, payments, shares and remaining bill debts. Generated records exclude private notes and account balances.
- Saved original photos can be shared as PDFs, with camera orientation preserved and long images continued across pages. Existing PDF attachments retain their original bytes. This path shares the actual bill, including everything visible on it, rather than substituting OCR text.
- OCR rows are compared using the printed text angle. A synthetic tilted receipt previously attached Tea's price to Coffee two rows later; it now retains each item's own price.
- Decimal commas retain paise, including `20,00`, `1234,56` and `1,234,56`. INR thousands grouping remains supported.
- Footer numbers after the final total are excluded from purchases. Intermediate page subtotals do not discard later items.

No Room schema, backup format, ledger arithmetic, model assets or Internet permissions changed. Recognition remains a reviewed draft; these fixes do not guarantee correct readings of every blurred or distorted photo.

## Broad app run

The broad run completed 343 cases: 309 passed, 33 failed and one assumption-based case did not run. The Gradle/UTP XML counts that assumption as a failure, giving 34 failure entries; it is not an additional app defect. The run preceded the final parser edge-case and PDF test-harness corrections. The full suite was not repeated after those corrections; final-source verification is the table above.

An emulator **System UI isn't responding** dialog held window focus during part of the run. It was confirmed using both window state and a screenshot, then dismissed using its Wait button. This particularly limits the broad run's real-system authentication evidence.

After clearing that dialog, the final 19-case receipt/authentication selection passed all 17 receipt cases and `AppLockActivityTest.coldStartAndBackgroundRequireAuthenticationAndProtectWindow`. `AppLockSystemAuthTest.deviceCredentialSuccessCancelAndBackgroundUseRealSystemResult` still failed at line 64, after PIN submission, matching the earlier audit's unresolved stage. That predicate accepts only Welcome/Today text, whereas fresh installations now route to balance setup. This is a concrete selector limitation; it does not independently prove that authentication completed correctly. Successful PIN completion, cancellation and subsequent relocking remain unverified by that test.

`ReceiptPdfTest.initializationError` was a new test-harness defect: an expression-bodied coroutine test inferred a Boolean return. Explicit Unit test bodies corrected it; all three actual PDF cases passed in the final run.

The history/reset fixtures use fixed October/November dates while account opening entries use the actual clock. For example, `ChatHistoryRepositoryTest.historicalGpayResetPreviewMatchesCommitWithoutLeakingPriorMonthCash` expected a November balance of 500000 paise, but its opening balance is now dated after November 1, producing 1000000 before import. That assertion is not evidence that the import itself duplicated money. Related dated fixtures still require correction and rerunning.

Many UI failures overlap the [earlier API 36 audit](2026-10-25-api36.md), which records stale labels, formatting and scrolling selectors. This does not establish that every remaining failure is harmless. They remain unresolved unless separately verified; application behavior was not changed to satisfy old screenshot assertions.

## Limits

API 26/API 35 devices, manufacturer camera behavior, severe blur/glare/perspective distortion, hardware authentication and production signing were not verified by this update. The existing 0.2.3 download predates these source changes. A passing receipt subset does not make the full app suite green.
